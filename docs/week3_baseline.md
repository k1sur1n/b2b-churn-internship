# Неделя 3 — Признаки, валидация, baseline-модели

## Цель недели

Построить и честно сравнить три модели по возрастанию сложности: правило,
логрегрессия, CatBoost — на правильной (out-of-time) схеме валидации.

## Что сделать

1. Расширить признаки в `src/features.py` по группам:
   - платежи (среднее/мин/макс, отношение последний месяц/среднее)
   - динамика (тренд, волатильность, число месяцев подряд снижения)
   - объём отношений (число активных услуг, срок жизни клиента)
   - сигналы боли (обращения в поддержку, задолженность)
   - категориальные (сегмент, продукт, регион)
2. В `src/validation.py` реализовать:
   - разбиение train/test по времени (out-of-time), НЕ случайное
   - `evaluate(y_true, y_score, label)`: ROC-AUC, PR-AUC, Precision@k, Lift@k
3. В `notebooks/03_baseline.ipynb`:
   - Baseline 0: правило (ранжирование по одному признаку падения платежа)
   - Baseline 1: логистическая регрессия (Pipeline с ColumnTransformer)
4. В `notebooks/04_features.ipynb`:
   - CatBoost с ранней остановкой на eval-срезе по времени
   - Ожидаемый порядок качества: правило < логрег < CatBoost
5. Сформулировать результат одной фразой на языке бизнеса: "в топ-10% клиентов
   по риску попадает X% всех будущих уходов, lift = Yx".

## Deliverable (что должно быть в PR)

- [ ] `src/validation.py` — функции `evaluate`, `precision_at_k`, `lift_at_k`
- [ ] `notebooks/03_baseline.ipynb` — правило + логрегрессия
- [ ] `notebooks/04_features.ipynb` — CatBoost, таблица метрик всех трёх моделей
- [ ] Одна фраза-вывод на языке бизнеса (lift, %, а не только ROC-AUC)

## На что обратит внимание ревьюер

- ROC-AUC в правдоподобном диапазоне 0.7–0.9 (не 0.99)
- CatBoost действительно обыгрывает логрегрессию и правило — если нет,
  разбираем на семинаре, в чём дело
- Используются ранжирующие метрики, а не accuracy
