# Словарь данных

Учебный синтетический датасет B2B-клиентов российской телеком-компании.
Период: 30 месяцев, **январь 2024 — июнь 2026**. Заголовки столбцов — на
английском (стандарт для рабочих данных), значения категориальных полей —
на русском (сегмент, регион, продукт, статус), как это обычно выглядит в
реальных данных российской компании.

Датасет состоит из двух связанных таблиц: `clients` (справочник, кто есть
кто) и `usage` (помесячные транзакционные данные). Связываются они по
`client_id`.

---

## 1. `data/raw/clients.xlsx` — справочник клиентов

Лист `Клиенты`. **50 400 строк**, один клиент = одна строка. Это
"статичный" справочник: каждое поле в нём — это факт о клиенте, который
либо не меняется во времени (сегмент, регион), либо меняется один раз
(дата расторжения).

| Столбец | Тип | Описание | Примеры значений |
|---|---|---|---|
| `client_id` | строка | Уникальный идентификатор клиента. Ключ для склейки с `usage`. | `CL000001`, `CL050400` |
| `segment` | категория | Размер бизнеса клиента. | `малый бизнес`, `средний бизнес`, `крупный бизнес` |
| `product` | категория | Основная услуга, на которую подключён клиент. | `интернет`, `мобильная связь`, `телефония`, `облачные сервисы` |
| `region` | категория | Регион присутствия клиента. | `Москва`, `Санкт-Петербург`, `Урал`, `Сибирь`, `Юг` |
| `company_name` | строка | Название компании-клиента (вымышленное). | `Вектор-482`, `Стройинвест-Урал` |
| `connection_date` | месяц (`YYYY-MM`) | Дата подключения клиента (начало отношений с компанией). Может быть раньше января 2024 — значит, клиент уже был подключён на момент начала периода наблюдения. | `2023-11`, `2024-06` |
| `termination_date` | месяц (`YYYY-MM`) или пусто | Дата явного расторжения договора. **Пусто**, если контракт формально не расторгнут (это не всегда значит, что клиент активно пользуется услугами — см. пункт про "тихий" отток ниже). | `2025-03`, пусто (`NaN`) |
| `current_status` | категория | Статус клиента **на момент выгрузки данных** (то есть на конец периода, июнь 2026), а не исторический статус на какую-то более раннюю дату. | `Активен`, `Расторгнут` |

### Важные нюансы по `clients.xlsx`

- **`segment` и `region` не меняются во времени** — это статичные атрибуты,
  их можно безопасно приджойнить к любому snapshot'у как признак.
- **`termination_date` заполнен только для явных расторжений.** Если
  клиент прекратил платить, но формально не расторгал договор ("тихий"/
  "спящий" отток), это поле останется пустым — такого клиента нужно
  вычислять по динамике `revenue` в таблице `usage`, а не по этому полю.
- **`current_status` — это срез на сегодня, а не история.** Если сейчас
  (в конце периода) клиент "Расторгнут", это поле будет говорить
  "Расторгнут" **независимо от того, из какой точки отсчёта (snapshot) вы
  смотрите** — даже если на момент этого snapshot клиент был ещё активен.
  Подумайте, что это значит, если использовать это поле как признак для
  прогноза на исторических датах (см. тетрадь, раздел 2.4, про data
  leakage).

## 2. `data/raw/usage/` — помесячное потребление (30 CSV-файлов)

Один файл на месяц: `2024-01.csv`, `2024-02.csv`, ..., `2026-06.csv` —
именно так на практике выглядят выгрузки биллинга из промышленных систем
(данные приходят порциями, а не одним файлом). Суммарно **~1 073 000 строк**
по всем файлам. Схема одинаковая во всех файлах:

| Столбец | Тип | Описание | Диапазон/примеры |
|---|---|---|---|
| `client_id` | строка | Ключ связи с `clients.xlsx`. | `CL000001` |
| `month` | месяц (`YYYY-MM`) | Месяц, к которому относится строка. Совпадает с именем файла. | `2024-01` |
| `revenue` | число (руб.) | Начисления клиенту за месяц. | от 0 до нескольких млн руб. (зависит от сегмента) |
| `traffic_gb` | число (ГБ) | Объём трафика за месяц. Примерно пропорционален `revenue`. | ≥ 0 |
| `n_tickets` | целое число | Число обращений в поддержку за месяц. | обычно 0-2, может расти перед уходом |
| `debt` | число (руб.) | Задолженность на конец месяца. В норме 0. | ≥ 0 |
| `n_sim` | целое число | Число активных SIM-карт/подключённых услуг у клиента. | зависит от сегмента: единицы (малый бизнес) — сотни (крупный бизнес) |

### Важные нюансы по `usage/`

- **Клиент присутствует в файлах не за весь период.** Если `connection_date`
  клиента позже января 2024 — более ранних строк для него не будет.
  Если клиент явно расторг договор — строк после месяца расторжения
  тоже не будет (клиент "пропадает" из данных, это нормально и отражает
  реальность: после расторжения биллинг для него просто не выставляется).
- **"Тихий" отток выглядит иначе.** Если контракт формально не расторгнут,
  но клиент фактически перестал пользоваться услугами, строки в `usage`
  продолжают существовать, но `revenue`, `traffic_gb` и `n_sim` резко и
  надолго падают почти до нуля (а не исчезают). Это тот случай, когда
  `termination_date` в `clients.xlsx` останется пустым, но по факту клиент
  ушёл — нужно определять по данным `usage`, а не по справочнику.
- **Файлы независимы друг от друга** — читать их нужно все и склеивать
  (см. код ниже), после чего сразу сохранять в parquet, а не работать с
  CSV напрямую (30 файлов по ~1.1-1.4 МБ каждый, суммарно ~43 МБ — терпимо,
  но склеенный CSV лучше сразу не трогать повторно).

### Как прочитать всё сразу

```python
import glob
import pandas as pd

clients = pd.read_excel("../data/raw/clients.xlsx")

usage_files = sorted(glob.glob("../data/raw/usage/*.csv"))
usage = pd.concat([pd.read_csv(f) for f in usage_files], ignore_index=True)

# дальше работайте только с parquet — так быстрее на объёме ~1 млн строк
clients.to_parquet("../data/processed/clients.parquet")
usage.to_parquet("../data/processed/usage.parquet")

print(clients.shape)  # (50400, 8)
print(usage.shape)    # (~1 073 000, 7)
```

### Как связать таблицы между собой

```python
usage_with_client_info = usage.merge(
    clients[["client_id", "segment", "product", "region"]],
    on="client_id",
    how="left",
)
```

`segment`, `product`, `region` можно смело джойнить как признаки на любой
snapshot — они не меняются во времени. `termination_date` и
`current_status` требуют аккуратности (см. предупреждения выше и тетрадь,
раздел 2.4).

## Полный список категориальных значений

Чтобы не было сюрпризов при `.unique()` / `.value_counts()`:

- **`segment`**: `малый бизнес`, `средний бизнес`, `крупный бизнес`
- **`product`**: `интернет`, `мобильная связь`, `телефония`, `облачные сервисы`
- **`region`**: `Москва`, `Санкт-Петербург`, `Урал`, `Сибирь`, `Юг`
- **`current_status`**: `Активен`, `Расторгнут`

Доля клиентов по сегментам **не равномерна** (малый бизнес — самая большая
доля, крупный бизнес — самая маленькая) — это сделано намеренно, чтобы при
разбиении на модели по сегментам (эксперимент A/B/C, неделя 4) был реальный
эффект нехватки данных в сегменте "крупный бизнес".

## Чего в данных нет

Проверено, чтобы вы не искали часами то, чего не существует:

- отрицательных `revenue` и `debt` — нет
- нулевых `revenue` — нет (минимум около 5.6 руб.)
- дубликатов по паре `(client_id, month)` — нет
- строк после `termination_date` и до `connection_date` — нет

Классической «грязи» в датасет не подсаживали. Проверять всё равно нужно, но
отрицательный результат — полноценный ответ: «проверил дубликаты и
отрицательные суммы, не найдено».

Настоящие сложности здесь другие: тихий отток, неравномерность сегментов,
разное присутствие клиентов в месяцах и скрытые бизнес-паттерны (см. ниже).
