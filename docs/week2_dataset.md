# Неделя 2 — Сборка обучающей выборки

## Цель недели

Собрать таблицу вида `client_id | snapshot_date | признаки | segment | product
| target`, где признаки строятся только из окна наблюдения, а таргет — только
из окна прогноза. Это самый важный этап всего проекта — большинство ошибок
происходит именно здесь.

## Что сделать

1. Зафиксировать письменно в `docs/journal_<имя>.md` определение таргета:
   - объект наблюдения (клиент/договор/услуга)
   - событие оттока (что именно считаем уходом)
   - длина окна наблюдения и окна прогноза
2. В `src/features.py` реализовать `build_snapshot(usage, clients, snapshot)`:
   - фильтрация "мёртвых душ" — брать только клиентов, активных на конец окна
     наблюдения
   - признаки — строго по данным до snapshot
   - таргет — строго по данным после snapshot
3. Собрать датасет по 5–6 точкам отсчёта (snapshot'ам), сохранить как
   `data/processed/dataset.parquet`.
4. Обязательные проверки в `notebooks/02_dataset.ipynb`:
   - доля оттока по snapshot'ам — стабильна (не скачет от 3% до 40%)
   - нет пропущенного сегмента после merge
   - один клиент в одном snapshot'е — ровно одна строка (assert)
5. Секция "самопроверка на утечку": по каждому признаку письменно ответить —
   "мог ли я знать это значение в 00:00 дня snapshot?".

## Deliverable (что должно быть в PR)

- [ ] `data/processed/dataset.parquet` (или воспроизводимый код его генерации)
- [ ] `notebooks/02_dataset.ipynb` со всеми проверками
- [ ] `src/features.py` — функция `build_snapshot`
- [ ] Зафиксированное определение таргета в журнале
- [ ] Явный список признаков с пометкой "точно не из будущего" по каждому

## На что обратит внимание ревьюер

- Есть ли утечка (проверка: специально даст датасет с "подставной" утечкой —
  должны найти)
- Не превышает ли итоговый ROC-AUC (когда дойдёте до недели 3) 0.95 —
  это красный флаг именно про сборку выборки
- Разбиение по времени, а не случайное — уже на этом этапе структура датасета
  должна это позволять
